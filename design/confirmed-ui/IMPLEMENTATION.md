# 界面实现与联调说明

本文件把确认稿转成前端可执行的布局和状态规则。业务数据字段、权限和错误码仍以 [`docs/SHARED_CONTRACT.md`](../../docs/SHARED_CONTRACT.md) 为准；不要从预览图推断新的 API 字段。

## 布局与视觉

- 统一白色顶栏与蓝色页面底。角色切换由登录账号决定，导航只显示该角色可用的入口；页面间不做白底/蓝底整页互换。
- 活动列表、我的报名、主办方管理、检票员工作区使用一张连续的暖白内容页，蓝色在外侧留出边距。列表项用分隔线和留白组织，不复制为大量漂浮小卡。
- 票正面是暖白纸卡，建议在桌面堆叠时宽约 `min(30vw, 500px)`，保持约 `0.70–0.75` 的宽高比；后方票只露约 16–32px。平铺演示为两列两行；真实列表少于四张就只显示真实票，多于四张继续滚动。
- 票背与正面同宽、正对视线，不倾斜成横向大面板。票背可随页面纵向增长；导航保持可见，交易哈希位于票内容最底部，靠滚动到达。长哈希允许换行、复制和打开链上详情。
- 票面标题用清晰的无衬线字，左对齐；上方小标签、下方局部插图，保留大块纸面留白。插图是活动的视觉表达，不承载二维码或交易数据。
- 可从确认图提取视觉方向，但不要把生成图作为最终票码、活动图或交易证据。实现时用真实可扫描二维码、项目自己的活动素材和 API 数据。
- 主要按钮沿用同一蓝色。状态主要靠文字和层级表达；不用红、绿、蓝整套状态色。文字最低保持正常可读大小，不为一屏塞下所有信息而缩小。

## 动效与操作

- 学生导航始终为三项。堆叠的 `Next ticket` 切换当前票；`Show me!` 或点当前票翻到背面；底部开关在堆叠与平铺之间切换。X 关闭背面并返回原来的堆叠/平铺位置。
- 翻票可用短促的 3D 翻转，但结束后票背必须放平；票背内容继续纵向滚动。页面内容切换约 200–300ms，避免发光、背景模糊和长距离弹跳。`prefers-reduced-motion` 时直接切换。
- 活动详情只有一个与当前状态相符的主要操作：可报名时报名、已报名时显示报名状态、中签且可领时领票、已持票时前往门票。状态以后端响应为准。
- 主办方创建活动从总览打开表单抽屉，字段遵守当前 `CreateEventInput`。活动详情根据 `OPEN`、`DRAWING`、`DRAWN`、`FINISHED` 切换操作；已完成抽签时不再提供可执行的抽签操作。链上记录仅展示已确认交易，点记录打开详情。
- 检票员必须先 `GET /tickets/:id` 核对，再由检票员触发 `POST /tickets/:id/redeem`。提交期间禁用重复操作；超时或 503 后重新查询票状态，不能擅自显示成功。成功结果包含确认后的 txId；失败结果单独替换成功区域。

## 转让流程与当前接口的差异

确认的界面方向包含**发起转让**和**接收方接受/拒绝邀请**。现有共享契约的 `POST /tickets/:id/transfer` 是发送方调用后立即转移票权，尚不能支持“待接收”状态；界面不能假装现有接口已经支持接受按钮。

建议三层联调时把流程改为：

1. 发送方在可转让票背面发起邀请，填写接收人的学生 ID。邀请先存普通业务库；此时票仍属于发送方，没有 `TICKET_TRANSFERRED` 链上记录。
2. 接收方在“我的门票”内部查看待接收邀请，可以接受或拒绝。接受前不显示可用票码。
3. 接受时后端重新校验票的当前持有人、活动开始时间、是否已核销和一次转让限制，再调用现有链码 `TransferTicket`；**链上确认后**接收方才成为持有人，票进入其门票堆，原持有人失去使用权。
4. 拒绝或邀请过期不产生票权交易；同一张票最多有一个待处理邀请。接口、持久化表与错误码需要三位同学同步更新共享契约后再实现。

这里是待联调的**契约变更点**，不是已实现的 API。任何真实页面应在接口落地后才启用接受操作。

## 占位内容与验收

- 所有截图中的 2025 年日期、演示姓名、人数、二维码、哈希和交易 ID 都只是排版占位；演示时必须替换为当前有效活动和真实响应。不能用截图二维码做扫码测试。
- 报名保存在平台业务库，不应显示成链上交易；票的领取、转让、核销等链上记录只在确认后出现。
- 学生真实门票数可能小于四张，平铺布局应自然适应；若答辩要演示完整 2×2，准备四张合法的演示票，不在前端造假票。
- 手机宽度下导航、票背二维码、检票输入/确认保持可用；桌面布局不应靠缩小字体强行塞进手机屏。
