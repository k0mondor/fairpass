# FairPass 展示视频录制操作清单

> 配套内容：[项目技术报告](PROJECT_TECHNICAL_REPORT.md)。适用于当前账号登录、用户名转让、提前验票及真实区块号查询版本。本文是录制操作脚本；最终视频与现场截图需由团队采集。

录制前先按第2节检查环境，并用单独活动完整走一遍创建、报名、抽签、领取、转让和核销。普通查询/演示登录等待12秒，其他POST写请求最多等待180秒；慢交易超过8秒会提示等待确认。历史加载失败应重试查询，不能把失败画面解释为没有链上记录。

## 1. 录制目标与素材版本

独立介绍版建议4—5分钟：问题背景、三角色功能、完整票务闭环、真实链上证据、总结。另剪约2分40秒功能版供7分钟答辩嵌入，保留创建/报名/抽签简短镜头、领取、转让、核销和历史。作业没有规定独立视频时长，这里是制作建议。

主线讲述：“主办方开放限额活动，学生报名，中签后领取，无法到场时转给另一位同学，活动开始前30分钟起检票入场，关键环节可以查到链上记录。”

## 3. 活动与时间安排：录制前先选方案

### 方案A：同一活动分段录制（推荐用于完整视频）

同一票串起领取、转让、核销和历史，最容易看懂。以开始录制前的本地时间T为基准，创建一个新活动：

| 字段 | 建议值 |
|---|---|
| 名称 | FairPass 展示专场 + 当天日期/场次 |
| 简介 | 校园活动限额报名、领票转让与现场核验演示 |
| 地点 | 校园大礼堂 |
| 容量 | 1（保证主线可控，不演示竞争公平性） |
| 报名截止 | T + 5分钟 |
| 活动开始 | T + 20分钟 |
| 活动结束 | T + 80分钟 |

创建表单是本地时间输入，代码会转成UTC；界面日期和时间统一显示UTC+8，与香港本地时间一致；接口与链上仍保存UTC ISO时间。以上时间留出了录制余量；若演练显示不够，创建前调大间隔。活动创建后不能修改时间。

只让alex报名，截止后抽签必然中签。完成领票与转让后，进入真实验票窗口（开场前30分钟起）再录核销，中间等待剪掉，字幕标“开场前验票”。不要修改系统时间、数据库或账本制造成功；链码会检查Fabric交易时间。

若要展示“名额少于报名人数”，另外录一个容量2、三学生报名的活动；中签结果随机，先查结果再确定谁领票，不预设alex一定中签。不要把单人中签镜头解释成对公平性的验证。

### 方案B：两个活动分别展示（适合答辩现场）

- 活动A尚未开始：录报名/抽签/领票/转让。
- 活动B正在进行，且已在开始前领到有效未核销票：录检票。B必须提前安排创建、截止、抽签和领票。
- 切换时字幕与讲解明确“以下使用另一场已进入验票窗口的活动展示核销”，不要剪成同一张票或同一活动的连续操作。

现有 `demo:prepare` 准备的 **Pass it on.** 开始时间在创建时约30天后，只适合现场领票、转让，不能立即核销。`demo:campus` 的四组校园票也不保证录制时正在进行，不能当作通用核销数据。

### 已有辅助脚本的正确使用

后端启动后，在WSL终端执行：

```bash
export PATH=/opt/fairpass-dev/node-v22.19.0-linux-x64/bin:$PATH
cd /opt/fairpass-dev/backend
npm run demo:campus
npm run demo:prepare
# 原票已经领取或转出，需要另一场演示活动时：
npm run demo:prepare -- --new
```

`demo:campus`会创建四组校园活动、报名、抽签并给alex领票，适合作为票堆展示素材；`demo:prepare`会创建活动、给alex报名和抽签，但故意保留“已中签未领票”。这些脚本会真实写数据，不能覆盖本次手工创建与报名镜头；没有必要时不执行。准备记录位于仓库 `.local/`，已有同名活动应按manifest和eventId核对；重复录制用新活动，不清账本。

## 4. 逐镜头操作与讲解词

以下按方案A执行。所有按钮文字以当前页面为准，进入正确业务页后等待加载完成。表格时长是剪辑后建议，真实录制可以多留停顿。

## 6. 录制中异常处理

| 现象 | 核对与恢复 |
|---|---|
| 页面显示预览、无真实交易 | 检查API环境变量，重启Vite；不要用预览镜头证明上链 |
| txId以mock-开头 | 后端是Mock，切换real并核对数据一致性后重新准备 |
| 创建/领取/转让卡住或报503 | 先重新查活动、门票、历史；超时可能已经提交，不连续点击 |
| 抽签入口不可用 | 确认主办方归属、截止已到、开始未到；重新打开详情刷新时间与状态 |
| alex不是中签者 | 多人竞争时属正常；查实际名单后选中签账号；稳定主线只让alex报名 |
| 无法领票或票已转出 | 本场已经用过，或已到开始时间；新建活动，不尝试回滚链状态 |
| 转让接收人不存在/格式错误 | 输入存在的学生用户名，如jamie；不填UUID或显示昵称 |
| 已到开始时间才想转让 | 已错过窗口，新建一场并留足时间 |
| 核销报CHECKIN_CLOSED | 核对本场开始/结束时间及UTC换算；Pass it on.默认约30天后开始 |
| 摄像头不支持 | 改手动票号查询；不影响后端合约核销演示 |
| 查不到某票或无权限 | 检查64位完整ticketId、当前账号和最新owner；原持有人转出后无权继续当持票人查看 |
| 二次核销按钮没有出现 | 已核销状态下前端已阻止，保留此镜头即可；不要声称录到了第二次API调用 |
| 历史区块号缺失或查询失败 | 检查后端为real模式及QSCC查询权限，恢复连接后重试；Mock不提供真实区块号 |

## 7. 配音与剪辑口径

可以说：“后端抽签、结果和资格上链”“链上保存当前票权”“真实commit确认后返回成功”“报名信息主要保存在SQLite”“转让最多一次、核销最多一次”。

避免说：“链上自动抽签、绝对公平”“所有数据都上链”“二维码完全防截图”“每个学生独立链签名”“完全去中心化”“已实现大规模校园商用”。这些超出了当前实现或验证范围。

剪掉等待与重复操作可以，但要保持因果顺序：报名截止后才抽签，活动开始前完成领取和转让，进入开场前30分钟窗口后核销。方案A保留同一票号作为衔接证据；方案B明确标注换活动。成功状态要等实际返回再录，不用剪辑把加载中拼接成已确认。
